# تأسيس Supabase لمشروع AMAN.C

## القرار
تم اعتماد Supabase أساسًا للخدمات الخلفية:
- PostgreSQL لقاعدة البيانات.
- Supabase Auth للمصادقة بالبريد الإلكتروني وكلمة المرور.
- Row Level Security (RLS) لعزل بيانات العملاء ومنع الوصول المباشر غير المصرح به.
- دوال PostgreSQL موثوقة (RPC) للعمليات الحساسة والذرّية.

## مصدر القواعد
تُطبق القواعد الوظيفية من مستودع AMAN.Y، الفرع `feature/aman-simplified-v2`، وبالأخص:
- `AMAN_ADMIN_OPERATIONS_REFERENCE_v1_0.md` — تنقيح 5.
- `docs/references/AMAN_CUSTOMER_UI_INTERACTION_CONTENT_REFERENCE_v1.0.md` — تنقيح 2.
- `docs/references/AMAN_DECISIONS_IMPLEMENTATION_REPORT.md`.

هذه المراجع قواعد وظيفية، وليست تعليمات لنسخ الكود القديم.

## ما أُضيف
- `supabase/migrations/20261101000100_initial_schema.sql`: تأسيس الجداول والعلاقات والقيود الأساسية.
- إنشاء ملف `profiles` تلقائيًا عند إنشاء مستخدم Auth، مع تعيين الدور `customer` من الخادم فقط.
- قيد يمنع وجود أكثر من مدير واحد.
- تفعيل RLS على جميع الجداول.
- لا توجد صلاحيات قراءة عامة. القراءة الذاتية الوحيدة الممنوحة حاليًا هي صف المستخدم في `profiles`.
- لا توجد بعد دوال اعتماد الطلبات أو البحث أو إنشاء الحماية أو إدارة المهام؛ لا تستخدم قاعدة البيانات للإنتاج قبل إضافة هذه الدوال والسياسات واختبارها.

## نقاط لم تُحسم ولا يجوز تخمينها
1. بيانات شركات الاتصالات والبادئات وأطوال الأرقام.
2. باقات الحماية الرسمية لكل شركة ولكل نوع عملية وأسعارها ومددها.
3. وسائل الدفع وتعليماتها وقواعد مرجع الدفع.
4. إعدادات مهام السداد لكل شركة.
5. إعدادات التنشيط: هل السماح وأيام السماح إعداد عام أم إعداد لكل شركة؟ القرار موثق كمسألة مفتوحة.
6. أربع نقاط مفتوحة في خوارزمية مهام السداد عند تغيير الفاصل والتنشيط وإغلاق المهام.

لا توجد بيانات أولية تجريبية أو شركات أو أسعار أو باقات مزروعة في المخطط.

## إنشاء مشروع Supabase وربطه
1. أنشئ مشروعًا جديدًا في لوحة Supabase باسم AMAN-C Production، واختر أقرب منطقة مناسبة لليمن/الشرق الأوسط إذا كانت متاحة، دون أن يؤثر ذلك على قاعدة التواريخ التي ستُحسب دائمًا وفق `Asia/Aden`.
2. احتفظ بكلمة مرور قاعدة البيانات في مدير كلمات مرور خاص بك. لا ترسلها في المحادثة.
3. من إعدادات المشروع انسخ **Project URL** و**Publishable key** (أو المفتاح العام `anon` في الواجهات القديمة). هذان مخصصان للاستخدام في العميل مع RLS.
4. لا تشارك مطلقًا `service_role` أو `secret key` أو كلمة مرور قاعدة البيانات. لا تضعها في ملفات HTML/JavaScript أو GitHub أو رسائل المحادثة.
5. لا تنشئ حساب مدير عبر التسجيل العام. سيُنشأ المدير الوحيد بإجراء إعداد آمن منفصل بعد بناء مسار التهيئة والتحقق من الدور.
6. لا تشغّل بيانات شركات أو باقات تجريبية. تُضاف البيانات الرسمية فقط بعد استلامها واعتمادها.

## تطبيق الترحيل
بعد إنشاء المشروع، يُطبّق ملف الترحيل من Supabase SQL Editor أو باستخدام Supabase CLI. قبل التطبيق على مشروع إنتاج، تُراجع نسخة احتياطية وخطة الاسترجاع. هذا الترحيل يجهز بنية أولية آمنة مغلقة افتراضيًا؛ لا يعني أن التطبيق أصبح متصلًا أو جاهزًا لتشغيل العملاء.

## المرحلة التالية
- إكمال مراجعة المخطط مقابل كل أقسام مرجع الإدارة.
- إضافة دوال RPC الذرّية: `lookup_number`, `submit_operation_request`, `review_operation_request`، ودوال المهام والبلاغات وتعطيل الحساب.
- كتابة سياسات القراءة الدقيقة واختبارات RLS للعميل والمدير ومحاولات الوصول بين العملاء.
- ربط المصادقة بالبريد الإلكتروني وكلمة المرور في الواجهتين.
- إعداد بيئة اختبار منفصلة عن الإنتاج واختبارات قاعدة البيانات قبل نشر أي مفاتيح عامة.
