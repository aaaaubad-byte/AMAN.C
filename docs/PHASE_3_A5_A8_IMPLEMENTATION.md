# تقرير تنفيذ المرحلة الثالثة — A5 إلى A8

التاريخ: 2026-11-01  
الفرع: `feature/phase-3-admin-a1-a4`

## النطاق المنفذ

| الشاشة | التنفيذ |
|---|---|
| A5 — تأكيد الاعتماد | نافذة تأكيد مستقلة تعرض معاينة الاعتماد القادمة من الخدمة الخلفية، ولا تسمح بالتنفيذ إلا بعد نجاح جلب المعاينة. ترسل `approveRequest` وتنتظر `success: true`، ثم تعيد تحميل التفاصيل والقائمة. |
| A6 — رفض الطلب | نافذة مستقلة، أسباب الرفض تُحمّل من `getRejectReasons` ولا تُنشأ محليًا، السبب إلزامي والتوضيح اختياري. ترسل `rejectRequest` وتنتظر تأكيد الخادم ثم تعيد تحميل التفاصيل والقائمة. |
| A7 — الأرقام | قائمة قابلة للبحث والتصفية حسب الحالات المعتمدة: الكل، محمي، غير نشط، منتهي/مصادَر. تعتمد على `listNumbers` ولا تعرض بيانات تجريبية. |
| A8 — تفاصيل الرقم | تعرض بيانات الرقم والفترة الحالية وسجل الفترات والأحداث والعملاء والطلبات والبلاغات والتنبيهات ومهام السداد وموعد المصادرة المتوقع وآخر يوم للتنشيط عند إرجاعها من الخدمة. شاشة قراءة فقط ولا تقدم إجراءات تشغيلية. |

## عقود الخدمات المطلوبة

- الموجودة من A1–A4: `getCurrentAdmin`, `signInAdmin`, `signOutAdmin`, `getDashboardSummary`, `listRequests`, `getRequestDetails`, `getApprovalPreview`, `getRejectReasons`, `approveRequest`, `rejectRequest`.
- الجديدة في هذه الدفعة: `listNumbers({ search, status })` وتعيد `{ success: true, numbers: [] }`.
- الجديدة في هذه الدفعة: `getNumberDetails({ number_id })` وتعيد `{ success: true, number: {...} }`.

## قواعد السلامة

- لا تُعرض بيانات بديلة أو تجريبية عند غياب الخدمة أو فشلها.
- تظل صلاحية المدير والتحقق من حالة الطلب ومنع التكرار والتحقق من أثر الاعتماد مسؤولية الخادم.
- يجب أن تكون عمليات الاعتماد والرفض ذرية ومسجلة في سجل التدقيق، مع إعادة التحقق من الحالة الحالية.
- تفاصيل الرقم للقراءة فقط؛ لا إضافة رقم ولا اشتراك ولا تمديد ولا تنشيط من لوحة الإدارة.
- لم تُنشأ قاعدة بيانات فعلية ولم تُطبق migrations ولم تُضف أسرار أو مفاتيح.

## حالة الاكتمال

هذه الدفعة تنفذ الواجهات وتعاقدات التكامل الأمامية. لا يوجد في المستودع حتى الآن تنفيذ خلفي موصول للعقود الجديدة أو القديمة؛ لذلك لا تعتبر عمليات الأرقام والقرارات متصلة تشغيليًا حتى توفير الخدمات الخلفية واختبار الصلاحيات وRLS وعمليات RPC. وجود النافذة أو القائمة لا يثبت نجاح العملية.

## التحقق المطلوب

- فحص صياغة JavaScript والروابط عبر GitHub Actions.
- اختبار يدوي بعد ربط الخدمات: A5 معاينة ثم اعتماد؛ A6 أسباب ثم رفض؛ A7 بحث/مرشحات؛ A8 فتح التفاصيل والرجوع.
- التحقق من عدم تسرب بيانات أرقام أو عملاء غير مخولين.
