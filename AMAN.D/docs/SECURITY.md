# الأمن والصلاحيات

## مفاتيح الاتصال

- المفتاح الموجود في الواجهة هو مفتاح Supabase العام المخصص للنشر.
- يُمنع تضمين service_role أو أي مفتاح سري في ملفات AMAN.D أو سجلات البناء.
- لا تضع كلمات المرور أو رموز الجلسات في السجلات أو رسائل الخطأ.

## المصادقة

- دخول العميل ودخول الإدارة عبر Supabase Auth.
- بعد دخول الإدارة، يستدعي المحوّل `admin_get_current` ويتحقق من أن الحساب مدير فعلي.
- لا تُعرض الشاشات الإدارية دون جلسة مدير مؤكدة.
- عند `auth_required` تُعاد واجهة العميل إلى تسجيل الدخول.
- عند انتهاء JWT، يسمح المحوّل بمحاولة واحدة بعد تجديد الجلسة. لا يعيد تنفيذ عملية مغيّرة تلقائيًا بعد انقطاع الاتصال، لتجنب تكرار العملية.

## صلاحيات قاعدة البيانات

- RLS مفعّل على جميع الجداول الـ22 وفق تقرير التدقيق.
- الوصول التشغيلي يمر عبر RPC المراجعة؛ لا تنفذ الواجهات استعلامات مباشرة على الجداول.
- دوال SECURITY DEFINER تتطلب عناية خاصة؛ لا تضف دوالًا أو صلاحيات جديدة دون قرار أمني ومراجعة.
- يجب أن تبقى صلاحية المدير محققة داخل قاعدة البيانات، لا في الواجهة فقط.

## التخزين والجلسات

تتولى طبقة المحوّل إدارة جلسات Supabase ومفاتيحها. لا تقرأ واجهات العميل والإدارة localStorage أو sessionStorage مباشرة. تفضيل السمة يُحفظ بواسطة `shared/theme.js`، وتخزين جلسات Supabase يتم داخل المحوّل/المكتبة.

تُحفظ أسماء مفاتيح الجلسات القديمة كما هي لضمان التوافق. لا تُغيّرها لمجرد إزالة اسم AMAN.C؛ ثبات قيمة المفتاح النصية لا يعني اعتمادًا تشغيليًا على ملفات المشروع القديم.

## Service Worker

- لا يخزن طلبات تحمل Authorization.
- لا يخزن استجابات private أو no-store أو no-cache أو must-revalidate.
- يرفض استجابات Set-Cookie وVary: *.
- يقتصر على الملفات الثابتة المحددة في قائمة السماح.
- لا يخزن نتائج RPC أو بيانات المستخدم.

## التعامل مع فشل الخدمة

النجاح لا يُعرض إلا عند `success: true` من الخدمة. إذا لم تصل نتيجة مؤكدة لعملية مغيّرة، يجب عرض حالة غير مؤكدة وطلب تحديث الحالة قبل إعادة المحاولة.
